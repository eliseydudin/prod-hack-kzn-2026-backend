# ADR001 - Выбор базы данных

Итоговое решение: использовать PostgreSQL через SQLModel (wrapper под SQLAlchemy).

- Для команды разработки было важнее запустить знакомый инструмент, из-за чего был выбран PostgreSQL.
- Для взаимодействия используем SQLModel (wrapper для SQLAlchemy), т.к. он оптимизирован для FastAPI.

# ADR002 - Идентификаторы в базе данных

Итоговое решение: приватный integer primary key + публичный snowflake ID.

- Нужно выбрать стратегию генерирования идентификаторов в базе данных.
- Классически в условиях хакатонов UUID используется как и primary key, так и идентификатор объекта. Проблема с данным подходом заключается в том, что поиск (а также добавление объектов в СУБД при условии использования MySQL/MariaDB) по UUID медленнее, чем обычных чисел. Это может сильно замедлить приложение в будущем.
- Другим подходом является использование autoincrement чисел, как идентификаторов. В теории злоумышленник может использовать идентификаторы, выданные через сервис, чтобы получить информацию об общем кол-ве объектов, или узнать идентификаторы удалённых, из-за чего это решение тоже отбрасывается.
- В итоге было принято решение использовать autoincrement primary key в самой базе данных, а пользователю пересылать unique ID.
- Вместо обычных UUID мы используем [Snowflake ID](https://en.wikipedia.org/wiki/Snowflake_ID), т.к. они специально были созданы для масштабируемых сервисов.

# ADR003 - Архитектура

Итоговое решение: использовать модульный монолит

- Для задачи с ограниченным сроком важно обеспечить быструю разработку и воспроизводимое демо.
- Большинство проектов на FastAPI используют монолитную архитектуру, что означает наличие большего количества ресурсов для обучения.
- Команда разработки лучше знакома с монолитной архитектурой.

# ADR004 - Хранилище типа ключ-значение

Итоговое решение: использовать Valkey.

- Для задачи с ограниченным сроком важно обеспечить быструю разработку и воспроизводимое демо.
- Вместо Redis используется Valkey, т.к. Valkey распространяется по более свободной лицензии (Apache v2.0).

# ADR005 - Файловое хранилище приложения

Итоговое решение: использовать RustFS.

- Идея написать собственную систему была отброшена на ранних этапах.
- Самым популярным хранилищем является AWS S3, но он требует денежных вложений.
- MinIO - главная альтернатива S3, но проект был закрыт 26 апреля 2026.
- Самой новой альтернативой является RustFS, из-за чего был выбран он.

# ADR006 - Метрики

Итоговое решение: использовать Sage

- Одним из критериев является сбор логов приложения, чтобы отслеживать неполадки.
- Так как Spirit рекоммендует использовать Sage, а также для него уже присутствовали готовые конфиги, было решено использовать именно его.

# ADR007 - Пуш уведомления

Итоговое решение: использовать Celery и pywebpush

- Пользователь создаёт события, которые имеют дату начала. Доп. функцией было придумано отсылать напоминания пользователю, чтобы он не пропустил отмеченные события.
- Чтобы не нагружать основной процесс, мы решили дополнительно разворачивать Celery Worker, использующий Valkey как брокера.
- Мы используем pywebpush для соответствия сервиса стандартам [Push API Mozilla](https://developer.mozilla.org/en-US/docs/Web/API/Push_API).
